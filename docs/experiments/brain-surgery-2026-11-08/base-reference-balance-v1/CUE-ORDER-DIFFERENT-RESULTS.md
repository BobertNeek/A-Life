# Different-history control reveals second-created-object bias

Eight post-hoc diagnostic CPU trials on already-used seed 2026111554: green/gray-green safe/harmful training, both test foods harmless red/blue with red physically left, safe-first exposure order, probe creation red-first vs blue-first × remembered-pain readout off/on × normal/fast-write-sham. The red-safe label is hypothetical in this different-color history; neither red nor blue was trained as safe. All training exposures were actual and all cold-next/optimizer checks passed.

In every red-first case (red ID 6, blue ID 7), the creature consumed blue. In every blue-first case (blue ID 6, red ID 7), it consumed red. Thus this one-seed different-history control chose the second-created object in all eight cases, regardless of memory readout or fast writes. This reveals a strong object-order/identity confound in this fixture; the earlier all-blue control cannot be interpreted as an innate blue preference. It does not establish the source of the bias, nor invalidate the separate single matched-history pilot in which the candidate chose safe red under both object orders. It means the earlier two-seed cue-history result needs a fresh matrix that independently counterbalances test-object creation order as well as cue mapping, side and exposure order. User was informed before any learned-preference claim.

`cue-order-different-summary.json` gives choices, IDs, actual training events and full-receipt hashes. No user life, default brain, GPU path or production environment switch was changed. This is a design-seed diagnostic, not a new independent learning result.
